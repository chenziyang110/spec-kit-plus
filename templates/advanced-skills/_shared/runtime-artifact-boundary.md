# Fixed Workflow Artifact Boundary

Treat canonical workflow artifacts as CLI-owned. Use `specify-runtime artifact show --path <project-relative-path> --view summary`, then targeted `--json-pointer`, `--section`, or `--limit`, before expanding to `--view full`. Mutate through the specialized owner named by the artifact registry. Generic `specify-runtime artifact prepare` / `specify-runtime artifact submit` is valid only when `prepare` grants a lease for an agent-editable type; submit bounded semantic content inline with `specify-runtime artifact submit --content '<payload>'`, never through a temporary file. The runtime validates path ownership, optimistic revision, single use, and atomic replacement. Use `artifact scaffold` only for a registered fixed shape. Do not directly read or overwrite canonical workflow artifacts. `workflow-state.md` is inside this boundary as rich semantic resume/evidence state and is never required-stage authority; CLI-owned `workflow.json` is accessed only through `specify-runtime workflow`. Source code, tests, and explicitly task-scoped implementation files remain normal repository edits.

If one corrected call returns the same `usage-error` or `invalid` summary and blocker, stop value-guessing: do not vary argument values or path syntax again. Inspect `show_argv`, run `specify-runtime api show <capability> --format json`, or use the namespace's supported `--help`, then make one contract-correct retry. An unchanged error after value-only edits means the option may not have been consumed.
