[AGENT] `sp-review` runs only against the candidate binding for the immutable candidate selected from implementation output. Execute Review work through `specify-runtime run supervise`, and bind frozen delivery targets through `specify-runtime review target-bind`; do not call direct integration from Review.

## Main Flow

1. Run `{SCRIPT}` to resolve one implemented feature and inspect repository status. Initial Review transitions from validated `implement`; an acceptance repair arrives through CLI-owned `accept route-repair` with `review` already active. Run `{{specify-subcmd:specify-runtime review prepare --feature-dir <feature-dir> --expected-revision <revision> --format json}}`; stop when the implementation handoff, fingerprint, prior approved Review digest, routed acceptance finding, or revision is missing, stale, or ambiguous. Acceptance repair must create the next immutable Review cycle rather than editing or reapproving the old cycle.
2. Query `implementation-handoff.json` and current `review-state.json` through targeted `specify-runtime artifact show` calls, including every confirmed deferral, required acceptance ref, and official entrypoint. Each DEF is unresolved scope transferred from Implement: restore its exact refs and withheld claims, then rerun it; never count it as prior PASS evidence.
3. Compile the bounded Review Universe from authoritative acceptance obligations, official entrypoints, changed consumer surfaces, runtime-discovered controls and registrations, and affected regression paths. Use independent coverage discovery so the handoff scenario matrix is a minimum rather than a blind spot; the Leader owns the zero-uncovered reconciliation. Before executing a heavyweight command or real scenario, inspect validation status and follow its `attempt_decision`. `remaining_epochs: 0` means no new logical gate slots, not that Review is dead: a returned `retry_same_gate` opens the next physical attempt inside delivery, while `repair_before_retry` requires diagnosis and a changed fingerprint. Scenario slices within that attempt share it rather than incrementing logical gate count.
4. Start the software from every applicable official real entrypoint and wait for its declared ready signal. The Leader orchestrates an independent read-only Review/Audit wave, joins every result, reconciles coverage, and forbids audit workers from editing product code or declaring coverage complete. Register/import all new scenario evidence through `specify-runtime evidence`, and submit every packet result inline through `specify-runtime result submit --command review`; the CLIs alone materialize current-cycle evidence and results, and earlier-cycle evidence cannot close the new cycle.
5. Exercise real actions and observable results inside that delivery attempt. Trace button, link, menu, form, command, route, handler, provider, factory, service, persistence or external dependency, and user feedback wiring where applicable. For UI scenarios capture integrated `structure_snapshot`, `visual_capture`, and `runtime_diagnostics` evidence from the real entrypoint once per applicable surface/fingerprint. Do not run the full viewport/state capture loop per Txx.
6. After the audit join, run an independent Fix wave for accepted findings. The Leader sends bounded Fix workers one or more accepted findings with authoritative expected behavior, isolated write scopes, forbidden truth artifacts, and exact regression obligations. Fix workers run cheap task checks and report test impact; they do not independently start heavyweight verification. Every approved-scope defect stays inside Review regardless of repair size: missing code, a task omission, incomplete tests, broken wiring, and an unknown root cause are not reasons to exit. Use a read-only diagnostic packet for an unknown root cause; Review remains the stage owner and then dispatches the repair itself.
7. Join and inspect every repair result, open a new attempt in the same delivery gate, restart the integrated product, and run an independent revalidation wave. A repair author must not verify its own finding; the Leader or a different read-only subagent reruns the exact failed journey, dependent scenarios, and credible regression set against the post-repair fingerprint. That bounded set attributes finding-level revalidation only: after any Fix, approval still requires every executable required Review scenario and all required evidence against the single final reviewed snapshot in that attempt. No pre-Fix scenario evidence can satisfy approval. Record the complete accepted Fix-set digest plus an exact byte-bound full-matrix evidence manifest in the final revalidation; partial, missing, extra, or relabeled scenario evidence also blocks approval. Timeout/termination is interrupted and may retry the same fingerprint; a real failure requires repair and a new fingerprint. Never open a fourth logical gate. Cycle 1 uses the same path, cycle-id, and byte-digest gates as later cycles. If—and only if—a required scenario cannot execute because named physical hardware is absent, use the deterministic hardware exception lane in the included shell contract. After bounded alternatives and byte-bound unavailability evidence, obtain explicit human confirmation of the exact digest. Record `waived` and `pass_with_waivers`, never PASS, exclude only that confirmed scenario from executable revalidation, and carry its withheld claims and residual risk forward.
8. Only a proven missing or contradictory requirement, design, or architecture truth may stop Review; missing code remains Review-owned repair and never reopens Implement. After all joins and zero uncovered obligations, prepare one compact target input per required Human Acceptance scenario: `id`, `mode`, official `entrypoint_id`, environment/instance/configuration refs, optional artifact/deployment/version fields, test-data refs, linked Review scenario ids, and fresh ready-evidence refs.
9. Bind every compact target through `{{specify-subcmd:specify-runtime review target-bind --feature-dir <feature-dir> --input-json '<compact-target-json>' --format json}}`. Never author the target row or identity JSON. The runtime verifies current-cycle evidence and product artifacts, derives `status`, the current implementation fingerprint, the canonical identity path and bytes, both byte/dataset digests, and atomically updates `review-state.json` plus the current-cycle identity file.
10. Run `{{specify-subcmd:specify-runtime review validate --feature-dir <feature-dir> --format json}}` and approve only with fresh cycle-specific integrated evidence, runtime-bound targets, and zero blocking findings. Then run `{{specify-subcmd:specify-runtime review closeout --feature-dir <feature-dir> --expected-revision <revision> --format json}}`, execute its returned workflow argv separately, recommend `{{invoke:accept}}`, and stop. The handoff preserves the frozen Human Acceptance Universe, targets, identity evidence, waiver ledger, withheld claims, and digests without prefilling human PASS; acceptance repair resets every human scenario.
